Sếp: "Em lấy giúp anh cái bảng giá bên site X nhé, chiều nay họp cần số liệu."
Mình: "Dạ, 30 phút."

Ba tiếng sau, mình vẫn ngồi trước màn hình F12, lẩm bẩm: "Ủa, sao cái class nó đổi rồi?"

Anh em làm scraping chắc không lạ gì cảnh này. Từ ngày đưa AI vào workflow, công việc đỡ đau hơn — nhưng không phải theo kiểu "một dòng lệnh lấy hết data" như mấy video trên mạng. AI giúp mình rút ngắn những đoạn lặp lại; còn việc lấy đúng dữ liệu, kiểm chứng kết quả và chịu trách nhiệm vẫn là phần của mình.

Workflow mình dùng: AI đề xuất, test xác nhận, người làm chịu trách nhiệm.

Bài này đi từ cách dùng AI cho selector và parser đến việc kiểm thử, giám sát scraper đang chạy; cuối cùng là những giới hạn cần cân nhắc trước khi tự động hóa.

🛑 Vấn đề: selector là bản hợp đồng không ai ký

Selector trong scraping có một đặc điểm rất "đau": nó phụ thuộc vào thứ mà chủ site không hề cam kết giữ nguyên.

  • Class bị hash: Tailwind, CSS Modules, styled-components... build mới cái là selector cũ tạch.
  • DOM đổi cấu trúc: Thêm một wrapper, đổi thứ tự cột, hoặc chuyển sang render client-side.
  • Data bẩn: Giá mỗi nơi một kiểu, ngày tháng mỗi nơi một format, tên sản phẩm dính ký tự ẩn.
  • Bảo trì: Chạy đúng một lần thì dễ. Chạy đúng 365 ngày mới là cực hình.

Luồng cũ của mình ngày trước gói gọn trong một câu: mở DevTools -> copy selector -> chạy -> site đổi -> sửa -> lặp lại. Một trang thì không sao. Mười trang, mỗi trang một kiểu, mỗi tuần vỡ một lần... đó là lúc mình nhận ra: scraping không khó ở chỗ viết code, nó khó ở chỗ giữ code chạy mãi.

🛠 AI giúp gì? (The Fix)

1. Đọc DOM và sinh selector

Thay vì tự dò từng node, mình lấy HTML đã rút gọn rồi quăng cho AI cùng một yêu cầu rõ ràng: ưu tiên data-*, itemprop, cấu trúc ngữ nghĩa; tránh class hash; và luôn kèm selector dự phòng.

Bạn là kỹ sư scraping. Dưới đây là HTML đã rút gọn của một trang danh sách sản phẩm.
Hãy trả về JSON gồm:
- selector CSS ổn định nhất cho: tên, giá, link, ngày đăng
- một selector dự phòng cho mỗi trường
- lý do chọn (ưu tiên data-*, itemprop, cấu trúc ngữ nghĩa; tránh class hash)
Không bịa trường không tồn tại trong HTML.

HTML:
<dán HTML đã rút gọn>

Nhưng nói thẳng: AI chỉ thấy đúng HTML mà bạn đưa. Nó không thấy trang đã render, không tự bấm nút "Xem thêm", không biết data nào được nạp bằng JavaScript. Bước lấy HTML đúng vẫn là việc của con người.

2. Viết parser và chuẩn hóa data

Đây là chỗ mình thấy AI đáng tiền nhất. Thay vì ngồi viết từng hàm xử lý giá, ngày, khoảng trắng, ký tự ẩn... mình mô tả schema mong muốn và để AI sinh parser kèm các case biên.

Ví dụ, yêu cầu AI viết schema Zod cho sản phẩm, kèm logic đổi "1.299.000₫" thành 1299000, và bỏ qua bản ghi thiếu trường bắt buộc. Mình không cần AI viết nhanh hơn mình. Mình cần nó ép mình nói rõ: đầu ra trông như thế nào, trường nào bắt buộc, data bẩn thì xử lý sao.

3. Đề xuất bản vá khi site đổi

Khi scraper toang, mình lưu HTML mới làm fixture, chạy test để biết trường nào chết, rồi đưa HTML + test fail cho AI. Nó thường đề xuất selector mới hoặc chỉnh parser khá nhanh. Nhưng đề xuất vẫn phải qua review và test. AI sửa đúng syntax không có nghĩa là sửa đúng data.

📋 Workflow thực chiến của mình

Bước 1: Check quyền và tìm API trước

Đừng thấy data là lao vào. Mình đọc robots.txt như một tín hiệu về chính sách crawl của site, kiểm tra điều khoản sử dụng và quyền sử dụng dữ liệu, rồi tìm API công khai hoặc kênh truy cập được cho phép. Có API phù hợp thì ưu tiên dùng API. Chỉ scrape HTML khi việc đó được phép và thực sự cần thiết. robots.txt tự nó không phải giấy phép sử dụng nội dung.

Bước 2: Lấy HTML và rút gọn

Site render client thì dùng Playwright thay vì fetch thuần. Lấy xong thì bỏ script, style, svg, mấy thuộc tính không cần thiết. HTML càng gọn, token càng rẻ, AI càng tập trung.

Bước 3: Nhờ AI đề xuất selector

Dùng prompt ở trên, nhưng giữ lại HTML mẫu trong repo để lần sau còn đối chiếu. Mẹo nhỏ: bắt AI trả JSON thay vì văn xuôi, để dán thẳng vào code hoặc so sánh giữa các lần chạy.

Bước 4: Code và validate

Đây là đoạn code tối giản mình hay dùng: Playwright lấy data, Zod check đầu ra. Selector trong ví dụ là giả định, anh em thay bằng selector AI đề xuất và đã kiểm chứng nhé.

import { chromium } from "playwright";
import { z } from "zod";

const ProductSchema = z.object({
  name: z.string().min(1),
  price: z.number().int().nonnegative(),
  url: z.string().url(),
});

type Product = z.infer<typeof ProductSchema>;

const toPrice = (raw: string): number | null => {
  const digits = raw.replace(/[^\d]/g, "");
  return digits ? Number(digits) : null;
};

export async function scrape(url: string): Promise<Product[]> {
  const browser = await chromium.launch();
  const page = await browser.newPage();

  try {
    await page.goto(url, { waitUntil: "domcontentloaded" });

    const raw = await page
      .locator("[data-testid='product-card']")
      .evaluateAll((nodes) =>
        nodes.map((node) => {
          const el = node as HTMLElement;
          const link = el.querySelector<HTMLAnchorElement>("a[href]");

          return {
            name:
              el.querySelector("[data-testid='product-name']")
                ?.textContent?.trim() ?? "",
            price:
              el.querySelector("[data-testid='product-price']")
                ?.textContent ?? "",
            url: link
              ? new URL(link.getAttribute("href") ?? "", location.href).href
              : "",
          };
        })
      );

    return raw.map((item) => {
      const price = toPrice(item.price);
      return ProductSchema.parse({ ...item, price });
    });
  } finally {
    await browser.close();
  }
}

Đoạn trên cố tình không có retry, cache hay xoay user-agent. Mấy thứ đó chỉ thêm khi có lý do rõ ràng, và phải nằm trong giới hạn site cho phép. Đừng biến scraper thành công cụ spam.

Bước 5: Giám sát và bảo trì

Scraper không giám sát là scraper sẽ âm thầm trả về 0 record. Mình lưu số bản ghi mỗi lần chạy, so với lần trước, và cảnh báo khi số lượng giảm bất thường. Có cảnh báo thì quay lại bước 3 với HTML mới. Vòng lặp này giờ ngắn hơn nhiều.

🧰 Cách dùng: 4 kiểu mình hay áp dụng

Nếu chỉ nói "dùng AI đi" thì chung quá. Mình chia thành 4 kiểu theo mức độ giao việc cho AI, từ nhẹ đến nặng. Anh em chọn kiểu nào cũng được, miễn là biết mình đang đánh đổi cái gì.

Kiểu 1: Hỏi selector (nhẹ nhất)

Mở ChatGPT/Claude/Gemini, dán đoạn HTML đã rút gọn, hỏi selector cho từng trường. Xong thì tự chạy thử, tự kiểm tra. Kiểu này phù hợp với site ít thay đổi, hoặc khi mình cần một scraper dùng một lần.

Ưu điểm là nhanh, không cần setup gì. Nhược điểm là mình vẫn phải tự verify từng selector, và HTML càng dài thì token càng tốn. Đừng dán cả trang 2MB vào prompt rồi hỏi "sao nó chậm".

Kiểu 2: Sinh scraper và test

Đưa AI HTML mẫu, schema đầu ra, và yêu cầu cụ thể: viết scraper bằng Playwright hoặc Cheerio, kèm test với fixture có sẵn. Mình thường bắt đầu bằng câu: "Viết test trước, rồi viết code cho pass test." Nghe hơi ngược đời nhưng hiệu quả, vì nó buộc AI phải bám vào dữ liệu thật thay vì đoán.

Kiểu này dùng cho scraper chạy định kỳ. Một lần setup hơi lâu, nhưng sau đó sửa chữa nhàn hơn nhiều. Và quan trọng: test là lưới an toàn khi AI đề xuất bản vá sai.

Kiểu 3: Dùng LLM như parser cho HTML "khó"

Có những trang mà selector không cứu nổi: data nằm trong text tự do, cấu trúc mỗi record một kiểu, hoặc HTML rối như canh hẹ. Lúc đó mình dùng LLM để trích xuất thẳng ra JSON theo schema, thay vì cố viết selector.

Trích xuất danh sách sản phẩm từ HTML dưới đây.
Trả về JSON đúng schema:
[{ "name": string, "price": number, "currency": "VND", "url": string }]

Quy tắc:
- Giá "1.299.000₫" -> 1299000
- Thiếu giá hoặc thiếu tên thì bỏ record
- Không suy diễn dữ liệu không có trong HTML
- Giữ nguyên tên sản phẩm, chỉ trim khoảng trắng

HTML:
<dán đoạn HTML cần trích xuất>

Cách này rất tiện cho volume nhỏ hoặc dữ liệu bán cấu trúc. Nhưng đừng mơ dùng nó cho 100.000 record mỗi ngày: chậm, tốn tiền, và không deterministic. Cùng một input, lần sau có thể ra kết quả hơi khác. Volume lớn thì selector + parser vẫn là vua.

Kiểu 4: Viết test, monitor và vá lỗi

Đây là kiểu mình dùng nhiều nhất sau khi scraper đã chạy ổn. AI viết test cho fixture, viết script so sánh số record giữa các lần chạy, và khi có cảnh báo thì đề xuất bản vá. Mình chỉ việc review, chạy test, rồi merge.

Nhưng nhớ: AI không biết site của mình quan trọng ở đâu. Nó không biết trường price mà sai thì cả dashboard sai. Business logic vẫn phải do mình viết test.

Chọn kiểu nào?

  • Trang ổn định, chạy một lần: Kiểu 1.
  • Chạy định kỳ, cần bảo trì: Kiểu 2 + 4.
  • HTML rối, volume nhỏ: Kiểu 3.
  • Scraper đang chạy và site vừa đổi: Kiểu 4.

⚖️ Pros/Cons: AI không phải cây đũa thần

Nói có sách, mách có chứng. Dưới đây là những gì mình thấy sau một thời gian dùng AI trong công việc scraping.

✅ Pros

  • Tốc độ: dựng scraper mới nhanh hơn rõ rệt, nhất là phần boilerplate và parse data bẩn.
  • Giảm đau bảo trì: site đổi thì có ngay phương án selector/parser mới để thử, thay vì ngồi mò cả buổi.
  • Xử lý data bẩn tốt: format giá, ngày, text đa ngôn ngữ, ký tự ẩn... AI xử lý mềm dẻo hơn regex thuần.
  • Học nhanh: không rành Playwright hay Cheerio vẫn có code mẫu để chạy thử và hiểu luồng.
  • Ép mình rõ ràng: muốn AI viết parser ổn, mình phải định nghĩa schema và edge case trước. Điều này tốt cho code.
  • Tiết kiệm thời gian chết: những việc lặp lại như viết test, đổi tên trường, format output... giao được hết.

❌ Cons

  • Bịa selector: AI có thể đưa selector không tồn tại, hoặc đúng với HTML mẫu nhưng sai với trang thật. Luôn test.
  • Không thấy trang rendered: nó không biết lazy-load, iframe, JS challenge hay nút "Xem thêm" nằm ở đâu.
  • Không deterministic: cùng prompt có thể ra kết quả khác nhau. Cần test, log và version prompt nếu dùng trong pipeline.
  • Chi phí và latency: LLM extract tốn token và chậm hơn selector thuần. Volume lớn là bài toán hoàn toàn khác.
  • Phụ thuộc dịch vụ: model đổi, API đổi, giá đổi, policy đổi. Pipeline của mình có thể gãy vì thứ ngoài tầm kiểm soát.
  • Rủi ro dữ liệu: dán HTML chứa thông tin khách hàng, token hay nội dung nội bộ lên prompt là tự mang rủi ro về mình.
  • Không giải quyết pháp lý hay anti-bot: captcha, ToS, robots.txt vẫn là việc của con người. AI không ký hộ mình cái hợp đồng trách nhiệm nào.
  • Debug khó hơn: output sai mà không biết do selector, parser hay model. Không có log và test rõ ràng là dễ mất phương hướng.

Khi nào nên / không nên

  • Nên: prototype nhanh, site bán cấu trúc, volume vừa phải, cần xử lý text bẩn, hoặc cần bảo trì scraper trong thời gian dài.
  • Không nên: volume cực lớn cần chi phí thấp, dữ liệu nhạy cảm, yêu cầu deterministic tuyệt đối, hoặc site cấm scraping.

Chốt một câu: AI giúp mình viết scraper nhanh hơn, nhưng không giúp mình trốn trách nhiệm. Chỗ nào cần độ chính xác tuyệt đối thì vẫn phải có test, log và người review.

⚠️ Ranh giới: đừng biến tool thành phá hoại

  • Captcha hay anti-bot: site chủ động chặn thì dừng. Đây là ranh giới, không phải thử thách.
  • robots.txt và điều khoản: data công khai không đồng nghĩa với việc được phép thu thập và tái sử dụng tùy ý.
  • Dữ liệu sau đăng nhập: không scrape dữ liệu riêng tư, hộp thư, thông tin thanh toán... của người khác.
  • Bản quyền nội dung: lấy data để phân tích khác với copy nguyên nội dung rồi đăng lại.
  • Dữ liệu cá nhân: đừng dán token, thông tin khách hàng, nội dung nội bộ lên prompt gửi ra ngoài.

Tool xịn đến đâu cũng không cứu được người dùng sai. Câu này mình nói thật.

📈 Kết luận

Với mình, scraping giờ bớt "đau" hơn rất nhiều. Những việc từng ngốn cả buổi — dò selector, viết parser, sửa khi site đổi — giờ gói lại trong vài vòng chat. Nhưng AI không thay mình hiểu dữ liệu, không thay mình kiểm tra kết quả, và càng không thay mình chịu trách nhiệm về cách thu thập dữ liệu.

Công thức của mình vẫn là: hiểu bài toán trước, để AI lo phần lặp lại, và luôn verify bằng data thật. AI là copilot. Người lái vẫn là anh em.

Nếu phải tóm gọn trong 3 gạch đầu dòng:

  • Dùng AI để nghĩ và viết phần lặp lại, không dùng để thay mình kiểm chứng.
  • Selector + test cho volume lớn; LLM extract cho dữ liệu khó và volume nhỏ.
  • Luật và đạo đức vẫn là phần con người phải tự chịu.
